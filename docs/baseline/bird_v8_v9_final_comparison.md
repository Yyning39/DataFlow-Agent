# v8 / v9 严格 A/B 对照报告

## 实验条件

- 同一 BIRD Mini-Dev SQLite manifest（22 条公开问题，manifest SHA-256 相同）。
- 同一模型 `deepseek-v4-flash`、`temperature=0`、provider `proxy/deepseek`、单题 60 秒上限。
- v8：`DBGPT_SCHEMA_HYBRID=false`，使用原 Chroma + 旧本地兜底。
- v9：`DBGPT_SCHEMA_HYBRID=true`，使用版本化本地词法 + hashing-vector 混合召回。
- 两组均 0 超时、0 配置不一致；DeepSeek 网关不返回 usage，因此成本保持不可用。

## 逐题变化与问题记录

- `european_football_2#1039`：v8 无 SQL，v9 正确生成平均值 JOIN 查询。
- `student_club#1331`：v8 无 SQL，v9 正确生成资金汇总查询。
- `european_football_2#1035`：v8 返回完整 161 行，v9 生成 `LIMIT 50`，结果被安全行数上限截断；这是“查询结果完整性/投影策略”回归，不能通过继续增加召回文档解决。

## 结论

v9 的主要成果是将“向量库空召回”转化为可观测、可缓存、可复现的本地混合召回，显著提高 SQL 可生成率、执行率和结果形状匹配率。当前准确率瓶颈已从 Schema 获取转移到模型 SQL 口径和安全行数策略；下一步应针对未显式要求限制条数的列表查询增加结果完整性决策，并继续保留大结果集保护。
