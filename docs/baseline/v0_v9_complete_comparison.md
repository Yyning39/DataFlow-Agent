# DB-GPT v0–v9 完整版本对比

## 1. 先说明数据口径

不同阶段的问题集和超时预算不完全相同，因此不能把所有历史数字放在一张“严格排名表”里：

- v0/v1：最初使用 Walmart 7 题基础集，适合证明原型可运行，不适合与 BIRD 22 题比较。
- v2/v3/v4：同一 BIRD Mini-Dev 22 题、同一模型和温度的严格版本消融。
- v5/v6/v7：主要是组件和线上专项能力迭代，没有各自独立的同条件全量准确率。
- v8/v9：重新使用同一 22 题、同一模型、温度 0、单题 60 秒完成严格 A/B；v8 关闭本地混合召回，v9 开启本地混合召回。

## 3. 每个版本到底改了什么

| 版本 | 核心改动 | 解决的问题 | 仍然存在的问题 |
|---|---|---|---|
| v0 原版 | DB-GPT 原始 DB Chat、Chroma、基础报告 | 验证自然语言转 SQL 原型 | 默认模型/Embedding 依赖外部服务；无统一 Guard、Trace、评测闭环 |
| v1 | MetricRegistry、只读 SQL Guard、有限纠错、Trace、评测脚本 | 指标映射、安全拦截、失败可追踪 | 基础集已接近满分，新增能力在简单题上体现不出来；延迟增加 |
| v2 | BIRD 公开集、Schema fallback、值提示、严格评测契约 | 新库向量摘要为空时仍能生成 SQL；开始量化端到端质量 | 值样例能证明编码存在，不能证明业务含义；严格正确率不稳定 |
| v3 | 配置化字段语义、同义词、value mapping、semantic decision、澄清阻断 | 解决 `Y/N`、`F/T`、代码值等业务语义歧义 | 语义覆盖依赖治理配置，复杂业务口径仍需人工定义 |
| v4 | 增强 SQL 结构/结果校验、权限边界、报告证据链、长尾超时保护 | 拦截危险 SQL、未知表、异常结果；支持 P50/P95 | Guard 能保证安全和可执行，不能保证业务结果正确 |
| v5 | 向量候选不足时按表名/列名补齐；新增 datasource-neutral `semantic_intent` | 避免空或不完整 Schema 直接放弃，并让语义状态可解释 | 底层 Chroma 空召回率仍为 100%，当时只是稳定 fallback |
| v6 | 两阶段 `SqlGuard.review`；证据支持的空结果大小写重试 | 结构校验与业务意图分层；修复低风险大小写错误 | 无证据不改 SQL；复杂 JOIN、聚合口径仍可能错误 |
| v7 | TTL/LRU SQL 结果缓存、用户 scope 隔离、可选模型路由、token/成本观测 | 重复查询降延迟，避免跨用户缓存泄漏，记录成本估算 | 默认缓存关闭；网关不返回 usage，成本只能保持 null |
| v8 | 分组维度语义修正、图表自动类型推断、前端 Diagnostics、权限/多轮/多源冒烟 | “按 gender 分组”不再被误判为缺少过滤值；产品闭环可展示 | Schema 仍依赖旧 fallback；模型仍可能产生错误投影或 LIMIT |
| v9 | D 盘版本化 Schema 文档；词法 + 256 维 hashing-vector 本地混合索引；缓存/回退诊断 | 把 Chroma 空召回转成可观测、可复现、可缓存的本地召回 | 当前仍未修复底层 Chroma embedding 服务；模型 SQL 口径和结果完整性成为主瓶颈 |

## 5. 能力成熟度结论

- 原型可用：v0–v2 已完成。
- Agent/语义能力：v3–v5 已完成，具备配置化指标、字段语义、歧义决策和 Schema 召回解释。
- 工程可靠性：v6–v7 已完成，具备安全 Guard、有限纠错、Trace、缓存隔离和成本观测。
- 产品展示：v8 已完成，具备图表、报告、Diagnostics、多轮和多数据源冒烟闭环。
- 检索增强：v9 已完成，具备版本化文档、本地混合召回、缓存和 fallback。

当前最准确的项目结论是：**SQL 生成和执行链路已经稳定可演示，Schema 获取问题已工程化解决；剩余主要误差来自模型业务口径、聚合/JOIN 逻辑和结果完整性策略，而不是“没有数据库能力”。**
